# 需求规格：对话运行时加固（chat-runtime-hardening）

## 背景与目标

客户现场（2026-10-24）一次反馈 6 项，全部落在**对话运行时**这一条链上：附件、生成物、思考展示、
工具熔断、模型超时、模型接入方式。其中 3 项是可复现的缺陷（已在 `bugs.md` 记账），4 项是能力增强（`backlog.md` 记账）：

| 客户问题 | 台账 | 类型 |
|---|---|---|
| 附件最多 5 个，要求调大（并问"最多能调到多少"） | BL-62 | 需求（限制放开 + 评估） |
| 智能体生成文件后，一定要提示生成附件的路径 | BL-63 | 需求 |
| qwen3.8 思考模式没展示（`Unsupported block type ThinkingBlock`） | BUG-201 | 缺陷 |
| 工具触发熔断，正常流程被打断 | BUG-202 | 缺陷 |
| 模型 180s 超时报错，但实际没断、稍后仍出结果 | BUG-203 | 缺陷 |
| 首帧超时时间要调大 | BL-64 | 需求（配置面） |
| 想用 Xorbits Inference（Xinference）调模型 | BL-65 | 需求（接入方式） |

**目标**：把这 6 项收口成一套**可配置、可解释、可预期**的对话运行时行为 ——

① 附件上限不再是魔法数字，而是**配置项**，且给出"最多能调到多少"的**有依据结论**（联动请求体、单文件大小、存储与上下文）；
② 智能体生成文件后，用户**一定能拿到路径/下载提示**，不靠猜；
③ 模型的思考（thinking）**能展示**，且历史消息回传时**不被静默丢弃**；
④ 工具熔断只对"**同工具 + 同参数连续重复**"生效，并按**会话**隔离计数，不再误伤多轮检索；
⑤ 首帧超时**可配置**，且超时后行为**语义一致**（要么真中断并说明，要么明确继续，不允许"报了超时却继续写"）；
⑥ Xinference 这类 **OpenAI 兼容**的自建推理服务能被接入（复用既有 provider 还是新增，由方案定）。

**成功长什么样（可度量）**：
- 改配置即可调整附件上限与首帧超时，**不需要改代码**；
- 生成文件的回复里出现可点击/可复制的路径；
- 用 qwen3.8（ollama 承载）对话时思考区有内容，多轮后历史里的 thinking 不丢；
- 同一智能体在两个并发会话中，一个会话的正常多轮检索**不会**因另一个会话的计数而被熔断；
- 超时日志与消息状态、实际产出**一致**（不允许 `model_timeout` 之后还继续 UPDATE 同一消息）；
- Xinference 的 `/v1/chat/completions` 能跑通一轮带工具调用的对话（流式）。

## 非目标（本 spec 不做）

- 不改模型侧（ollama / dashscope / Xinference）的推理实现，只做**接入与展示**；
- 不重做附件存储方案（仍走 `tbl_data_chat_attachment` + 现有上传接口），只放开数量上限与提示；
- 不做"思考内容入库/审计"（是否持久化 thinking 全文留给方案评估，默认不新增表）；
- 不引进新的外网依赖：Xinference 按**内网自建**假设接入。

## 需求条款

### R-01 对话附件数量上限可配置，并给出"最多可调到多少"的评估结论
WHEN 用户在一次对话中附加文件,
系统 SHALL 允许的数量上限取自**配置项**（不再是硬编码 5），并 SHALL 在前端给出明确提示（超限时的文案含当前上限）。
该配置 SHALL 有**依据性评估**：与单文件体积上限、请求体大小（nginx `client_max_body_size`）、
附件解析耗时/内存、模型上下文占用联动，形成"推荐值 + 安全上限"两档结论。

#### 验收场景
- Given 配置项改为 N, When 一次附加 N 个文件并发送, Then 全部上传成功且被模型上下文装配（不多不少）。
- Given 一次附加 N+1 个文件, Then 前端即时拦截并提示"最多 N 个"，后端亦拒绝（双端一致）。
- Given 评估结论文档, Then 明确写出"推荐默认值 / 安全上限 / 触顶时的表现"，并有实测数据支撑。

### R-02 智能体生成文件后，回复中必须给出附件路径/下载提示
WHEN 智能体在一次对话中生成文件（如 docx/xlsx/csv）,
系统 SHALL 在该轮回复中输出**生成物的路径或下载入口**（可点击/可复制），
且 SHALL 在会话历史中可再次取到（刷新/重进会话不丢）。

#### 验收场景
- Given 一次生成 docx 的对话, Then 回复里出现该文件的绝对路径或下载链接。
- Given 刷新页面并重进该会话, Then 仍能看到该生成物入口并成功下载。

### R-03 首帧超时可配置，且超时行为语义一致（修 BUG-203）
WHEN 模型在首帧超时时间内无任何产出,
系统 SHALL 按**配置**的超时时间处理（默认值由方案给出，客户期望显著大于 180s），
并 SHALL 保证"超时"与"实际产出"语义一致：一旦判定超时并落 `model_timeout`，
**不得**再继续追加/覆盖同一条消息内容；若选择继续等待，则不得提前写超时状态。

#### 验收场景
- Given 首帧超时配置为 600s, When 模型 5 分钟才出首个 token, Then 不报超时、正常出结果。
- Given 超时确实发生, Then 消息状态为终态且后续无新内容写入（同一 message id 不再 UPDATE）。
- Given 用户重试, Then 生成新消息而不是复用已超时消息。

### R-04 思考（thinking）内容可展示，且历史回传不丢失（修 BUG-201）
WHEN 使用带思考能力的模型（如 qwen3.8，经 ollama 承载）,
系统 SHALL 在对话界面展示该轮的思考过程（可折叠），
并 SHALL 在把历史消息回传给模型时**保留或正确降级** thinking 块，不得静默丢弃（当前 `OllamaChatFormatter`
反复告警 `Unsupported block type ThinkingBlock in the message, skipped`）。

#### 验收场景
- Given 一轮带 thinking 的问答, Then 界面出现思考区且内容非空。
- Given 连续多轮（≥3）带工具调用的对话, Then 历史回传不再出现 ThinkingBlock 丢弃告警，且模型能基于历史继续。

### R-05 工具熔断判定修正：同参数连续重复才熔断，计数按会话隔离（修 BUG-202）
WHEN 智能体连续发起工具调用,
系统 SHALL 仅在"**同一工具 + 同一参数**连续重复达到阈值"时熔断，
且计数 SHALL 按**会话（session/turn）**隔离，不得跨会话共享；阈值 SHALL 可配置。
参数发生变化 SHALL 清零计数（无论当前计了几种签名）。

#### 验收场景
- Given 同一会话内 5 次不同 query 的检索, Then 不熔断。
- Given 两个并发会话交替调用同一工具（参数不同）, Then 互不影响、都不熔断。
- Given 同参数连续调用达到阈值, Then 熔断并给出可读原因（保留现有文案能力）。

### R-06 支持 Xorbits Inference（Xinference）作为模型提供方
WHEN 运维希望用自建 Xinference 提供 chat / embedding,
系统 SHALL 支持配置其 `base_url`（OpenAI 兼容 `/v1`）与模型名并可正常对话（含流式与工具调用）；
采用"复用既有 provider"还是"新增 provider 枚举"，由方案评估后决定，但 SHALL NOT 要求改数据库结构。

#### 验收场景
- Given 一台内网 Xinference（`/v1/chat/completions`、`/v1/embeddings`）, Then 配置后在对话/向量检索中可用。
- Given 流式对话, Then 前端能正常增量渲染（不整段回吐）。

## 约束与关联

- **版本口径**：挂 **v2.1.0**（用户 2026-10-24 口令「还是 2.1.0」），与 `release-delivery-hardening`、
  `vector-dim-flexibility` 同版；不改既有 API 契约（除新增可选参数/字段）。
- **缺陷处置口径**：先**定位根因**（结论写入 plan.md 的「根因诊断」章节）再修；未定位清楚前不改代码。
- **台账**：BUG-201 / BUG-202 / BUG-203；BL-62 / BL-63 / BL-64 / BL-65。
- **兼容**：附件上限、超时时间的默认值必须**保持现网行为不倒退**（默认值变更需在变更说明中显式标注）。
