# 需求规格：组管理界面治理（group-management-ui）

## 背景与目标

用户在组管理列表页（后台）反馈三点（2026-10-24，`BL-69`；相关 `BUG-206` 已核实并**关闭为非缺陷**）：

| 现象 | 核实结论 |
|---|---|
| 状态显示"禁用"但看不到修改状态的入口 | **按钮存在**，但操作列现有 **7 个动作**（分配人员 / 分配智能体 / 分配知识库 / 分配技能 / 分配 MCP / 编辑 / 禁用-启用），状态切换被**挤出可视区** ⇒ 根因是操作列拥挤，不是功能缺失 |
| 操作列「配置（分配）智能体 / 知识库 / 技能 / MCP」没用，可删 | 当前仍在行内，占用列宽；实际使用频率低 |
| 需要「查看详情」能看到组的人员 | **无该入口**；现只有「分配人员」（编辑态）。后端已有 `GET /platform/account-group-info/group/{groupId}` 可查组成员 |

**目标**：

① 操作列**收敛为 3 个动作**（查看详情 / 编辑 / 启用-禁用），状态切换**永远可见**；
② 新增**组详情视图**，承载"组信息 + 组人员 + 各类分配"能力，作为原行内分配入口的新家；
③ **不动后端接口契约**（分配能力只是换入口，不是重做后端）。

**成功长什么样（可度量）**：

- 组管理列表每行**只有 3 个**操作按钮；1440 宽度下「禁用/启用」**完整可见不被截断**；
- 点「查看详情」能在 1 次交互内看到**组信息 + 成员列表**；
- 将任意成员/智能体/知识库/技能/MCP 的分配动作在详情页内完成，**后端接口与行为不变**；
- 原有列表分页、搜索、状态筛选、新建/编辑/删除组行为**不回归**。

## 需求条款（EARS）

- **R-01 操作列收敛**：WHEN 用户打开组管理列表页, 系统 SHALL 在每行仅展示「查看详情」「编辑」「启用」或「禁用」三个操作；分配类动作（人员/智能体/知识库/技能/MCP）SHALL NOT 出现在列表行内。
- **R-02 状态切换可见性**：WHEN 组状态为禁用（status=1）或启用（status=0）, 系统 SHALL 在同一行直接可见对应的「启用」/「禁用」按钮，且在 1440×900 视口下不得被遮挡、截断或折叠进"更多"。
- **R-03 详情视图（组信息）**：WHEN 用户点击某行的「查看详情」, 系统 SHALL 打开详情视图并展示该组的：名称、编码（sn）、状态、描述、创建时间、更新时间。
- **R-04 详情视图（组人员，后端分页）**：WHEN 详情视图打开, 系统 SHALL 在「人员」页签**分页**列出该组成员，每行至少含账号、姓名、角色/类型、加入时间；分页由**后端**提供（默认每页 20，可翻页/改页大小），前端不得一次性拉全量成员。
- **R-05 详情页承载分配与移除**：WHEN 用户具备该组的写权限, 系统 SHALL 在详情视图内提供「人员 / 智能体 / 知识库 / 技能 / MCP」五个页签的**授予与移除**入口；其中**人员移除**必须可用（复用 `DELETE /platform/account-group-info/group/{groupId}/account/{accountId}`）。
- **R-06 只读降级**：WHEN 用户不具备写权限, 系统 SHALL 在详情视图内以只读方式展示各页签内容（不显示授予/移除等写操作），且「查看详情」入口本身仍可用。
- **R-07 后端接口：既有不改、允许新增**：WHEN 原行内分配入口迁入详情页, 系统 SHALL 保持既有接口（`/platform/group-info/*`、`/platform/account-group-info/*`、`/platform/group-agent-info/*`、`/platform/group-kbase/*`、`/platform/group-skill/*`、`/platform/group-mcp/*`）的路径/参数/语义不变；为满足 R-04 的**后端分页**，允许**新增**成员分页接口或给既有成员查询接口**新增可选分页参数**（向后兼容）。
- **R-08 状态语义保持**：WHEN 展示或切换组状态, 系统 SHALL 维持 `0=启用 / 1=禁用` 的组域语义（双账号体系历史差异，本需求不"统一"）。
- **R-09 列表与详情一致性**：WHEN 在详情页完成分配或移除后返回列表, 系统 SHALL 使列表展示与最新数据一致（至少：重新进入详情或刷新列表后不出现陈旧数据）。
- **R-11 详情页数量概览**：WHEN 详情视图打开, 系统 SHALL 在顶部展示该组「人员/智能体/知识库/技能/MCP」的**已授权数量**概览（只读，不做批量操作）；数量 SHALL 与各域列表接口返回一致。
- **R-10 既有能力不回归**：WHEN 本需求上线后, 组管理原有能力（分页、按名称/状态筛选、新建、编辑、删除、状态切换）SHALL 保持可用且行为不变。

## 验收场景

**R-01**
- GIVEN 存在 3 个组, WHEN 打开组管理列表, THEN 每行操作区恰好是「查看详情 | 编辑 | 启用/禁用」三项，无「分配…」字样。

**R-02**
- GIVEN 某组 status=1（禁用）, WHEN 打开列表且视口 1440×900, THEN 该行「启用」按钮完整可见、可点击；反向（status=0 → 「禁用」）同样成立。

**R-03**
- GIVEN 组「G1」存在, WHEN 点击其「查看详情」, THEN 视图显示 G1 的名称/编码/状态/描述/创建时间/更新时间，且与 `GET /platform/group-info/{id}` 返回一致。

**R-04**
- GIVEN 组「G1」有 3 名成员, WHEN 打开详情「人员」页签, THEN 列出 3 行（账号/姓名/角色/加入时间）；
- GIVEN 组「G2」有 45 名成员, WHEN 打开「人员」页签, THEN 分页展示（每页 20，页码可翻）。

**R-05**
- GIVEN 用户有写权限, WHEN 在详情「知识库」页签执行授予, THEN 授予成功、页签内列表即时反映；对应后端请求与原行内入口一致。

**R-06**
- GIVEN 用户仅有只读权限, WHEN 打开详情, THEN 各页签有内容但无授予/移除按钮，且无报错。

**R-07**
- GIVEN 本次改动上线后, WHEN 检查网络请求, THEN `/platform/account-group-info/*`、`/platform/group-info/*` 的路径与参数与改动前一致（无删改）。

**R-08**
- GIVEN 某组 status=1, WHEN 切换状态, THEN 请求发往 `PUT /platform/group-info/{id}/toggle-status`，后端置为 0（启用），列表状态标签随之变化。

**R-09**
- GIVEN 在详情页移除成员 A, WHEN 关闭详情返回列表并刷新, THEN 详情再次打开时 A 不再出现（无陈旧缓存）。

**R-04（分页，后端）**
- GIVEN 组「G2」有 45 名成员, WHEN 打开「人员」页签（默认每页 20）, THEN 首页 20 行、共 3 页可翻；
- WHEN 请求成员列表, THEN 网络请求携带分页参数（`page`/`size` 或等价），**不是**一次返回 45 条。

**R-11（数量概览）**
- GIVEN 组「G1」有 3 名成员、2 个智能体、1 个知识库、0 个技能、4 个 MCP, WHEN 打开详情, THEN 概览显示 3/2/1/0/4，且与五个列表接口返回条数一致。

**R-10**
- GIVEN 本需求上线, WHEN 依次执行：搜索「G1」、按状态筛选、新建组、编辑组、删除组、切换状态, THEN 六项行为与改动前一致（逐项记录实测输出）。

## 非目标（本 spec 不做）

- 不改组状态的 `0/1` 语义，不做账号域与组域的状态统一；
- 不改后端接口契约（除非后续确认某分配接口零引用，另行决策）；
- 不改组的新建/编辑/删除业务逻辑与字段校验；
- 不改账号管理、角色管理页面的操作列；
- 不做移动端（`mobile-ui`）组管理；
- 不做批量分配/批量移除；
- 不调整权限模型与角色定义（沿用现有按钮/路由权限判定）。

## 我正在做的假设

1. **已定**：详情视图采用**抽屉（Drawer）**（用户 2026-10-24 决策）。
2. **已定**：成员分页由**后端**提供（用户 2026-10-24 决策）；实现上可给 `GET /platform/account-group-info/group/{groupId}` 新增可选分页参数，或新增分页接口；姓名等账号字段的装配方式由 plan 决策（需避免 N+1）。
3. **已定**：分页走后端（见 R-04）。
4. 权限沿用现有 vben 按钮/路由权限（`hasAccessByCodes`），本需求**不新增权限码**。
5. 仅改 `web-frontend/apps/admin-ui` 桌面端，技术栈（Vue3 + Element Plus + vben）不变。
6. **已定**：详情页人员页签需要"移除成员"（用户 2026-10-24 决策），复用既有 `DELETE /platform/account-group-info/group/{groupId}/account/{accountId}`。
7. 知识库/技能/MCP 的"移除"当前语义是**整体覆盖式 assign**（提交完整 id 列表）；详情页沿用该语义，不新增单个删除接口。
8. 数量概览通过调用五个列表接口取长度实现（5 个请求），不新增统计接口；若 plan 评估请求过多，可改为一次聚合（属新增，plan 决策）。
