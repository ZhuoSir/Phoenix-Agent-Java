# 需求规格：超长文档分批处理（long-doc-chunking）

## 背景与目标

当前单个附件抽取后**硬截断**：`ChatDocumentExtractor.MAX_EXTRACT_CHARS = 24000`（字符），
超出部分**直接丢弃**，仅提示「已按顺序截断至前 24000 字符（超出部分不参与理解）」。
后果：长文档（标准原文、制度汇编、招标文件）后半段内容模型**完全看不到**，回答只能基于前半段。

**目标**：超长附件内容**全部参与理解** —— 按内容切块、逐批处理、汇总作答；超限不再是"丢弃"。

**成功长什么样（可度量）**：
- 一份 5 万字的 docx，提问"第 4 章第 3 条怎么规定"，**能答对**（内容来自被原截断方案丢弃的后半段）；
- 处理过程用户**可见进度**（正在处理第 x/y 批）；
- 单轮 token 花费**有上限护栏**，不会因文档过大而无限调用模型；
- 超过上限的极端文档**明确降级并告知**（走摘要+索引或提示拆分），不静默丢内容。

## 需求条款（EARS）

- **R-01 切片**：WHEN 附件抽取文本超过配置阈值, 系统 SHALL 按语义边界（标题/段落/分页符）切分为多块，块间保留 overlap（重叠），不得在句子中间硬切。
- **R-02 逐批处理**：WHEN 存在多个块, 系统 SHALL **按顺序逐批**送入模型处理（抽取要点/摘要或回答问题），并把逐批结果汇总后再作答。
- **R-03 全量覆盖**：WHEN 文档被切分为 N 块, 系统 SHALL 处理**全部 N 块**（受 R-06 护栏限制时按 R-07 降级），不得出现"只处理前若干块"的静默丢弃。
- **R-04 进度可见**：WHILE 分批处理进行中, 系统 SHALL 向用户展示进度（如「正在处理第 3/8 批」），并在最终回答中标注「本文档共 N 块，已全部处理」。
- **R-05 阈值可配置**：WHEN 需要调整触发分批的字符阈值, 系统 SHALL 通过**配置项**调整（不重新编译）。
- **R-06 成本护栏**：WHEN 批次数量或累计 token 将超过配置上限, 系统 SHALL 在超限前停止并进入 R-07 降级路径。
- **R-07 超限降级**：WHEN 超出护栏, 系统 SHALL 明确告知用户「文档过大，已按摘要方式处理（覆盖全文）/建议拆分上传」，且**不得谎称已处理全文**。
- **R-08 失败与重试**：WHEN 某批次调用失败, 系统 SHALL 重试该批次（有限次）；仍失败则整体降级并说明失败批次范围。
- **R-09 幂等与可追踪**：WHEN 同一附件在同轮被处理, 系统 SHALL 保证批次处理幂等（不重复计费/重复写入），并在日志中记录 `attachmentId`、批次数、耗时。
- **R-10 兼容**：WHEN 文档未超阈值, 系统 SHALL 保持现有单批行为不变（不引入额外模型调用）。

## 验收场景

**R-01/R-02/R-03**
- GIVEN 一份 5 万字 docx, WHEN 提问"第 4 章第 3 条内容", THEN 回答包含该条内容（来自原截断丢弃的后半段），且回答中标注总块数。

**R-04**
- GIVEN 文档被切为 8 块, WHEN 处理进行中, THEN 前端/消息流出现「正在处理第 x/8 批」；结束后出现「共 8 块，已全部处理」。

**R-05**
- GIVEN 将阈值配置改为 1000 字符, WHEN 上传 2000 字文档, THEN 触发分批（无需改代码/重启打包）。

**R-06/R-07**
- GIVEN 一份 50 万字文档, WHEN 批次数超过护栏, THEN 停止并提示"文档过大，已按摘要方式处理"，不得声称已处理全文。

**R-08**
- GIVEN 第 3 批调用失败, WHEN 重试后仍失败, THEN 提示"第 3 批处理失败，其余 N-1 批已完成"。

**R-10**
- GIVEN 一份 5000 字文档, WHEN 提问, THEN 与现状一致（单次模型调用，无分批提示）。

## 非目标（本 spec 不做）

- 不做 RAG 索引化（向量化/检索路径）；本 spec 只做"同轮内分批理解"
- 不改附件上传/存储（仍走 `tbl_data_chat_attachment`）
- 不改模型侧能力（不要求模型支持超长上下文）
- 不做跨轮的文档知识沉淀（会话结束后不保留分块结果）
- 不做 PDF 扫描件 OCR（仍沿用现有 Tika 抽取结果）

## 我正在做的假设

1. 分批粒度按**字符/近似 token** 估算（项目当前无 tokenizer 依赖），阈值与每批大小均可配置。
2. 采用 **map-reduce**：每批让模型抽要点/回答子问题 → 汇总批结果再让模型生成最终回答（而非把全部块拼进一次上下文）。
3. 进度通过现有 SSE 帧（`content`/`notice`）透出，不新增前端组件。
4. **已定（用户 2026-10-24）**：触发阈值 **24000 字符**、每批 **6000 字符**、单文档最多 **20 批**；均可配置。
5. 与 BL-72（抽取上限配置化）合并落地：本 spec 一并把 `MAX_EXTRACT_CHARS` 变成配置项。
6. **已定（用户 2026-10-24）**：超出护栏时采用「**摘要方式覆盖全文** + 明确提示」降级，不直接报错、不谎称已处理全文。
