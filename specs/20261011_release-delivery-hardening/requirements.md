# 需求规格：交付链加固（release-delivery-hardening）

## 背景与目标

v2.0.0 发版与现场交付暴露出一整条**交付链的脆弱面**：两个架构包底座不一致、包内不含离线 Docker 引擎、
安装器对旧版 Compose 无友好拦截、维度迁移靠手工 SQL 且会误伤唯一约束、出货前没有任何自动化自检。
这些问题都不是业务功能缺陷，而是**"包能不能装上、装上能不能跑、出事能不能自查"**的问题，且每次都要靠
现场踩坑才发现（BUG-189~195 即为同一批）。

**目标**：把交付链从"靠人盯"变成"靠流程闸"——任一新版本打包时，**底座一致、离线可装、环境不满足即明确拒绝、
迁移安全可回滚、出货四项自检全绿**，使交付包在目标机上"要么一次装成，要么明确告诉我缺什么"。

**成功长什么样（可度量）**：
- 同一版本的两个架构包，基础镜像/运行用户/JDK 语义**完全一致**（manifest 可核对）
- 目标机无 Docker 且无外网时，`install.sh` 仍能完成引擎安装并跑到第 9 步收据
- 只装 Compose v1 的机器上，`install.sh` **在步骤 6 之前**失败并打印可照做的安装指引（不产生半启动栈）
- 维度迁移脚本在**任何**既有库上执行后，主键/唯一约束 **零丢失**，且迁移后维度与约束自检通过
- 出货流程对四个致命项（空库安装/jar 权限/sha256 格式/Compose 版本）**自动化自检**，任一不过即拒发

## 需求条款

### R-01 两架构交付包运行底座一致
WHEN 打包流程产出同一版本的 arm64 与 amd64 交付包,
系统 SHALL 使用同一套基础镜像体系（同一 JDK 发行版与主版本、同一运行用户 UID、同一应用目录约定），
且两包的 `manifest.json` SHALL 记录可核对的基础镜像标识，`JAVA_BIN` 语义 SHALL 一致。
IF 某架构的官方基础镜像不可获取, THEN 流程 SHALL 明确失败并给出替代方案说明（不得静默改用不同底座出货）。

#### 验收场景
- **GIVEN** 打包机可获取两架构基础镜像
  **WHEN** 执行一次打包产出两个包
  **THEN** 两包 manifest 的基础镜像标识一致/等价，且在 arm64 与 x86_64 上分别 `install.sh` 均到第 9 步收据
- **GIVEN** 某架构官方基础镜像不可获取（如受限网络）
  **WHEN** 执行打包
  **THEN** 流程以非 0 退出并输出"哪一层不可得 + 可选替代 + 影响"，**不产出**底座不一致的包

### R-02 交付包内置离线 Docker 引擎安装件
WHERE 目标机无可用 Docker 且无外网,
打包流程 SHALL 携带与包架构匹配的引擎离线安装件，使 `install.sh` 的引擎安装步骤 SHALL 能在纯离线条件下完成安装；
IF 离线件缺失或安装失败, THEN 安装器 SHALL 明确报错并给出手工安装指引（不得跳过继续后续步骤）。

#### 验收场景
- **GIVEN** 一台无 Docker、无外网的 Linux 目标机
  **WHEN** 执行 `install.sh`
  **THEN** 引擎被装上（`docker version` 可用）、后续步骤继续到收据
- **GIVEN** 目标机已有可用 Docker
  **WHEN** 执行 `install.sh`
  **THEN** 跳过引擎安装（幂等），不重复安装、不回退版本

### R-03 安装器强制 Compose v2 检测与指引
IF 目标机的 Compose 能力不是 v2（仅有 `docker-compose` v1 或均无）,
THEN 安装器 SHALL 在容器启动步骤之前**显式失败**，输出：检测结论、所需能力、可照做的安装指引（含系统级插件路径），
且 SHALL NOT 退回 v1 执行、SHALL NOT 留下已创建但未就绪的容器栈。

#### 验收场景
- **GIVEN** 目标机仅存在 `docker-compose` v1
  **WHEN** 执行 `install.sh`
  **THEN** 在步骤 6 之前失败、退出码非 0、日志含明确指引；`docker ps -a` 无本项目残留容器
- **GIVEN** 目标机具备 Compose v2
  **WHEN** 执行 `install.sh`
  **THEN** 正常继续（不受本约束影响）

### R-04 向量维度迁移加固与约束自检
WHEN 运维执行向量维度迁移,
系统 SHALL 提供迁移工具/脚本，其在删除向量索引时 SHALL 排除承载主键/唯一约束的索引；
迁移完成后 SHALL 自检：①所有含 embedding 列的表维度一致于目标维度 ②每表在 id 上存在唯一约束；
IF 自检不通过, THEN 输出不通过项与可照做的修复语句（如表存在重复 id，给出查重与去重语句）。

#### 验收场景
- **GIVEN** 库中各向量表的 id 上均有主键、embedding 上另有 hnsw 索引
  **WHEN** 执行迁移
  **THEN** 迁移后主键仍在（约束数不减）、hnsw 索引已重建、维度=目标值
- **GIVEN** 某向量表缺少 id 唯一约束
  **WHEN** 执行迁移与自检
  **THEN** 自检报出该表并打印 `ADD CONSTRAINT ... PRIMARY KEY (id)` 形式的修复语句
- **GIVEN** 某表 id 存在重复
  **WHEN** 执行迁移
  **THEN** 不静默删数据；报出重复组数并给出查重/去重语句

### R-05 出货门禁四项自检
WHEN 打包流程准备出货交付包,
系统 SHALL 自动执行四项自检：①全新空库安装（清空卷后 `install.sh` 到收据）②镜像内应用 jar 对运行用户可读
③包内 `.sha256`/`SHA256SUMS` 可被标准校验命令通过 ④目标机前置（Compose v2、架构匹配）声明与检测一致；
IF 任一项失败, THEN 流程 SHALL 拒绝出货（非 0 退出）并保留失败证据。

#### 验收场景
- **GIVEN** 故意把镜像内 jar 权限改成 0600（模拟回归）
  **WHEN** 执行出货自检
  **THEN** 门禁拒绝出货，日志指出"jar 权限"项失败
- **GIVEN** 四项均通过
  **WHEN** 执行出货
  **THEN** 出货成功并落盘自检凭据（含四项的真实命令输出）

### R-06 v2.1.0 交付包重打与发布通道
WHEN 本版本冻结后执行重打,
系统 SHALL 产出 `phoenix-2.1.0-{arm64,amd64}` 交付包（版本号一致、含 `SHA256SUMS` 与 manifest），
SHALL 通过 `install.sh` 端到端实测（两架构各一次到收据），
并 SHALL 给出发布通道可执行方案（含单文件体积上限约束下的分卷或替代存储方案）。

#### 验收场景
- **GIVEN** 版本已冻结
  **WHEN** 分别解包两架构交付包并执行 `install.sh`
  **THEN** 均到第 9 步收据；首页可访问、admin 可登录、升级台账为终值
- **GIVEN** 发布通道为 GitHub Release（单文件上限 2GiB）
  **WHEN** 上传两个包
  **THEN** 体积在限内直接上传；超限或网络不可达时给出分卷/替代存储的可执行步骤

## Non-goals（范围外）

- **不做**向量维度的"运行时灵活配置/多模型并存"（BL-61 已登记，另立 spec）
- **不做**应用代码与数据库结构变更（本版仅脚本、构建链、交付件与运维工具）
- **不做** Windows/PowerShell 侧改造（`install.ps1` 已有 hotfix 线）
- **不做**私有镜像仓库/镜像分发体系搭建（仍按"拷贝包 + install.sh"交付）
- **不做**前端与业务功能

## 我正在做的假设

1. 目标机为 Linux（以 Debian 系为主），架构为 arm64 或 amd64；**目标机可无外网**
2. 打包机可访问 Docker Hub 或镜像站以拉取基础镜像；受限时按 R-01 明确失败
3. 交付形态仍是"运维手工拷贝交付包 + 执行 `install.sh`"（不做自动分发/在线安装）
4. 现有 4 张向量表结构不变，本版只处理维度与约束（BL-61 另行处理结构灵活化）
5. 现场库（目标机）可停机数分钟执行迁移

现在纠正，否则按此执行。

- **Q3（阻塞 R-06）**：发布通道以 **GitHub Release** 为准（含分卷方案）吗？还是走内网文件服务器/对象存储？——影响是否要做分卷与校验脚本
- **Q4（阻塞 R-04）**：维度迁移工具形态——**独立运维脚本**（随包交付、`docker exec` 执行）还是平台内运维入口（页面/接口）？我倾向独立脚本（本版不改应用代码）
