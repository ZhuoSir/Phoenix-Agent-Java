# 需求规格：交付链加固（release-delivery-hardening）

## 背景与目标

v2.0.0 发版与现场交付暴露出一整条**交付链的脆弱面**：两个架构包底座不一致、包内不含离线 Docker 引擎、
安装器对旧版 Compose 无友好拦截、维度迁移靠手工 SQL 且会误伤唯一约束、出货前没有任何自动化自检。
这些问题都不是业务功能缺陷，而是**"包能不能装上、装上能不能跑、出事能不能自查"**的问题，且每次都要靠
现场踩坑才发现（BUG-189~195 即为同一批）。

**目标**：把交付链从"靠人盯"变成"靠流程闸"——任一新版本打包时，**底座差异显式可控、离线可装、环境不满足即明确拒绝、
迁移安全可回滚、出货四项自检全绿**，使交付包在目标机上"要么一次装成，要么明确告诉我缺什么"。

**成功长什么样（可度量）**：
- 同一版本的两个架构包，底座差异**显式记录**（manifest 可核对），且两架构各跑一次 `install.sh` 均到第 9 步收据
- 目标机无 Docker 且无外网时，`install.sh` 用包内**通用静态二进制**完成引擎落地并跑到第 9 步收据
- 只装 Compose v1 的机器上，`install.sh` **在步骤 6 之前**失败并打印可照做的安装指引（不产生半启动栈）
- 维度迁移脚本在**任何**既有库上执行后，主键/唯一约束 **零丢失**，且迁移后维度与约束自检通过
- 出货流程对四个致命项（空库安装/jar 权限/sha256 格式/Compose 版本）**自动化自检**，任一不过即拒发

## 需求条款

### R-01 两架构交付包的底座差异显式可控
WHEN 打包流程产出同一版本的 arm64 与 amd64 交付包,
系统 SHALL 优先使用同一套基础镜像体系（同一 JDK 发行版与主版本、同一运行用户 UID、同一应用目录约定），
且两包的 `manifest.json` SHALL 逐架构记录实际使用的基础镜像标识与等价性说明。
IF 某架构的官方基础镜像不可获取, THEN 流程 SHALL 允许改用替代底座（如通用 JRE 镜像），
但 SHALL 在 manifest 与交付说明中**显式记录差异**（哪一架构用了什么底座、`JAVA_BIN` 语义、已知影响），
且两架构 SHALL 各自通过 `install.sh` 端到端验证（到收据）后方可出货。

#### 验收场景
- **GIVEN** 打包机可获取两架构官方基础镜像
  **WHEN** 执行一次打包
  **THEN** 两包 manifest 记录同一底座标识，且在两类架构目标机上 `install.sh` 均到第 9 步收据
- **GIVEN** 某架构官方基础镜像不可获取（受限网络）
  **WHEN** 执行打包
  **THEN** 使用替代底座并**成功产出**，manifest/交付说明含差异记录（架构↔底座↔JDK 语义↔影响），流程不静默
- **GIVEN** 已产出存在底座差异的两个包
  **WHEN** 出货复核
  **THEN** 差异记录可被逐项核对，且两架构各自的安装验证证据齐备

### R-02 交付包内置通用静态二进制形式的离线 Docker 引擎件
WHERE 目标机无可用 Docker 且无外网,
打包流程 SHALL 携带与包架构匹配的**通用静态二进制**引擎件（如 `docker-<ver>.tgz`，非发行版专属包），
使 `install.sh` 的引擎安装步骤 SHALL 能在纯离线条件下完成落地（二进制就位 + 守护进程可用 + 开机自启配置）；
IF 离线件缺失或落地失败, THEN 安装器 SHALL 明确报错并给出手工安装指引（不得跳过继续后续步骤）。

#### 验收场景
- **GIVEN** 一台无 Docker、无外网的 Linux 目标机（非 Debian 系亦可）
  **WHEN** 执行 `install.sh`
  **THEN** `docker version` 可用、引擎自启已配置、后续步骤继续到收据
- **GIVEN** 目标机已有可用 Docker
  **WHEN** 执行 `install.sh`
  **THEN** 跳过引擎安装（幂等），不重复安装、不回退版本
- **GIVEN** 包内离线件与目标机架构不匹配
  **WHEN** 执行 `install.sh`
  **THEN** 明确报出架构不匹配并停止（不尝试安装不匹配的二进制）

### R-03 安装器强制 Compose v2 检测与指引
IF 目标机的 Compose 能力不是 v2（仅有 `docker-compose` v1 或均无）,
THEN 安装器 SHALL 在容器启动步骤之前**显式失败**，输出：检测结论、所需能力、可照做的安装指引（含系统级插件路径），
且 SHALL NOT 退回 v1 执行、SHALL NOT 留下已创建但未就绪的容器栈。

#### 验收场景
- **GIVEN** 目标机仅存在 `docker-compose` v1
  **WHEN** 执行 `install.sh`
  **THEN** 在步骤 6 之前失败、退出码非 0、日志含明确指引；`docker ps -a` 无本项目残留容器
- **GIVEN** 目标机具备 Compose v2
  **WHEN** 执行 `install.sh`
  **THEN** 正常继续（不受本约束影响）

### R-04 向量维度迁移加固与约束自检（独立运维脚本形态）
WHEN 运维执行向量维度迁移,
系统 SHALL 提供**随交付包分发的独立运维脚本**（不依赖平台页面/接口），
其在删除向量索引时 SHALL 排除承载主键/唯一约束的索引；
迁移完成后 SHALL 自检：①所有含 embedding 列的表维度一致于目标维度 ②每表在 id 上存在唯一约束；
IF 自检不通过, THEN 输出不通过项与可照做的修复语句（如表存在重复 id，给出查重与去重语句）。

#### 验收场景
- **GIVEN** 库中各向量表的 id 上均有主键、embedding 上另有 hnsw 索引
  **WHEN** 执行迁移脚本
  **THEN** 迁移后主键仍在（约束数不减）、hnsw 索引已重建、维度=目标值
- **GIVEN** 某向量表缺少 id 唯一约束
  **WHEN** 执行迁移与自检
  **THEN** 自检报出该表并打印 `ADD CONSTRAINT ... PRIMARY KEY (id)` 形式的修复语句
- **GIVEN** 某表 id 存在重复
  **WHEN** 执行迁移
  **THEN** 不静默删数据；报出重复组数并给出查重/去重语句

### R-05 出货门禁四项自检
WHEN 打包流程准备出货交付包,
系统 SHALL 自动执行四项自检：①全新空库安装（清空卷后 `install.sh` 到收据）②镜像内应用 jar 对运行用户可读
③包内 `.sha256`/`SHA256SUMS` 可被标准校验命令通过 ④目标机前置（Compose v2、架构匹配）声明与检测一致；
IF 任一项失败, THEN 流程 SHALL 拒绝出货（非 0 退出）并保留失败证据。

#### 验收场景
- **GIVEN** 故意把镜像内 jar 权限改成 0600（模拟回归）
  **WHEN** 执行出货自检
  **THEN** 门禁拒绝出货，日志指出"jar 权限"项失败
- **GIVEN** 四项均通过
  **WHEN** 执行出货
  **THEN** 出货成功并落盘自检凭据（含四项的真实命令输出）

## Non-goals（范围外）

- **不做**发布通道建设（GitHub Release/分卷/对象存储）——用户 2026-10-11 裁决，见 R-06 删除留史
- **不做**向量维度的"运行时灵活配置/多模型并存"（BL-61 已登记，另立 spec）
- **不做**应用代码与数据库结构变更（本版仅脚本、构建链、交付件与运维工具）
- **不做**发行版专属包（deb/rpm）——离线引擎件限定为**通用静态二进制**（用户 2026-10-11 裁决）
- **不做** Windows/PowerShell 侧改造（`install.ps1` 已有 hotfix 线）
- **不做**前端与业务功能

## 我正在做的假设

1. 目标机为 Linux，架构为 arm64 或 amd64；**目标机可无外网、可不属 Debian 系**
2. 打包机可访问 Docker Hub 或镜像站；某架构官方镜像不可得时按 R-01 用替代底座并记录差异
3. 交付形态仍是"运维手工拷贝交付包 + 执行 `install.sh`"（不做自动分发/在线安装）
4. 现有 4 张向量表结构不变，本版只处理维度与约束（BL-61 另行处理结构灵活化）
5. 现场库（目标机）可停机数分钟执行迁移

现在纠正，否则按此执行。
