## 方案概述

五条工作流，均为**平台层**改动；**不依赖单表混维度**（实测否决，见决策 1）：

| 流 | 需求 | 落点（拟） |
|---|---|---|
| **W1 绑定与建库** | R-01 | `KnowledgeBase` 增绑定字段（模型 id + `model_space_key`）；`KnowledgeBaseServiceImpl` 创建/编辑路径；前端知识库表单增"向量模型"下拉（默认=默认模型、可改选）；编辑换模型走受控重建 |
| **W2 模型→表映射** | R-02 / R-06 | 每模型一套向量表 `<原表名>__<模型键短哈希>`（列上保留该模型确定维度）；表按需创建（首绑即建，含 hnsw 索引）；`DataAgentConfiguration` 按"库→模型→表"装配 `PgVectorStore` 实例（框架一实例一表）；向量空间键写入并落库 |
| **W3 按库检索与扇出** | R-03 | `EvidenceRecallNode` 检索链路：解析命中知识库 → 按 `model_space_key` 分组 → 各组用各自模型嵌入查询 → 各表检索 → **RRF 融合** → 交给对话模型；不可达模型 ⇒ 关键词兜底 + 显式提示；查询嵌入按模型缓存 |
| **W4 删除受控与重建** | R-04 | 模型删除前置拦截（影响面清单 + 重建规模预估 + 禁删默认/最后可用模型）；后台重建任务（进度/失败重试/断点续跑/原子切换绑定）；窗口期检索降级并提示 |
| **W5 校验重构与升级** | R-05 / R-07 / R-08 / R-09 | `EmbeddingDimensionResolver` 由"全表一致"改为"按库绑定模型判定"；升级件分两路径（**模型明确 ⇒ 人工确认后搬迁不重嵌**；否则 ⇒ 重建）；运维工具箱脚本（体检/迁移/自检/验收报告）随交付包分发 |

## 涉及模块与数据流

```
前端 知识库表单(新增"向量模型"下拉)
  └─► KnowledgeBaseServiceImpl ──► tbl_data_knowledge_base(+embedding_model_id, +model_space_key)
                                    └─► 确保该模型的向量表存在（建表+索引）

写入: AgentVectorStoreServiceImpl.addDocuments
  └─► 解析所属知识库 → 取其绑定模型 → 选对应表/store → 维度校验(按库，R-05) → 写入

检索: EvidenceRecallNode（意图识别命中知识库）
  └─► 命中库集合 → 按 model_space_key 分组 → 各组: 该模型嵌入查询(缓存) → 该表 hnsw 检索
        → RRF 融合（名次）→ (可选文本 reranker) → 上下文
        └─ 模型不可达 → 关键词兜底 + 结果中标注"未参与语义检索"

模型配置: ModelConfigOpsService（删除/默认切换）
  └─► 删除前置校验(被引用? 默认? 最后一个?) → 影响面清单 → 确认 → 重建任务 → 原子切换绑定
  └─► 默认切换 → 仅影响"新建库的默认选项"，不动既有库绑定（R-01）

运维: docker/scripts/vector-dim-migrate.sh（已有）+ 本版新增：归属体检 / 表-模型迁移 / 验收报告
```
**改动面**：`phoenix-data-api`（实体/BO）、`phoenix-data-core`（KB 服务、向量存储装配、维度校验、检索节点、模型配置服务）、前端知识库表单与模型管理页、`sql/`+`releases/`（升级件）、`docker/scripts/`（工具箱）。
**不动**：hnsw/cosine 检索算法、框架 `PgVectorStore` 底层实现（按"一实例一表"复用）。

## 关键决策

### 决策 1：每模型一套向量表（而非"删掉表级维度/单表混维度"）
- **采用**：表名 `<原表名>__<模型键短哈希>`，列上保留该模型确定维度 ⇒ **hnsw 索引可用**、物理隔离、复用框架"一实例一表"
- **拒绝 A（单表 + 无 typmod 列 + dims 列）**：本机 pgvector **0.8.7 实测**——无维度列**无法建 hnsw 索引**（`ERROR: column does not have dimensions`，部分索引同样失败）⇒ 检索退化为全表扫描
- **拒绝 B（单表 + 每模型一向量列）**：列随模型增长、稀疏、且需自定义 store（偏离框架默认结构）
- **拒绝 C（按维度分表）**：维度相同的不同模型**空间不可比**，按维度分表会把两个模型塞进同一张表 ⇒ 语义错误

### 决策 2：绑定在创建时由用户选择（默认=默认模型），不做隐式跟随
- **采用**：R-01 语义——表单默认选中默认模型、用户可改选；绑定持久化；后续默认变更不影响既有库
- **拒绝 A**：隐式"跟随默认"——改默认会连带影响一大片库（2026-10-11 现场即此类牵连的教训）
- **拒绝 B**：不允许用户选择——无法满足"一库一模型"的灵活诉求

### 决策 3：删除模型必须过闸（影响面 + 重建 + 护栏）
- **采用**：前置清单 → 确认 → 后台重建 → 原子切换；禁删默认模型与最后一个可用模型
- **拒绝 A**：直接软删配置、向量静默失效——正是本次暴露的"删了模型才发现查不到"
- **拒绝 B**：删除即同步重建（阻塞式）——大库会长时间不可用，且失败无法续跑

### 决策 4：结构升级"搬迁不重嵌"必须**人工确认**
- **采用**：有归属证据（模型明确且可用）时提供搬迁路径，但需人工确认后执行（Q4 已确认）
- **拒绝 A**：自动搬迁——一旦"生成模型"判定错，会把向量放进错误的空间且无人察觉
- **拒绝 B**：一律重建——对"模型明确"的大库是巨大的算力/时间浪费

### 决策 5：多库跨模型检索用**分组扇出 + RRF**
- **采用**：按 `model_space_key` 分组、各自嵌入与检索、按名次融合
- **拒绝 A**：只用一个模型查全部库——跨空间比较无意义，等于漏查
- **拒绝 B**：分数归一化后加权——不同模型分数分布不可比，归一化假设不成立

### 决策 6：平台能力 + 就地工具箱双交付
- **采用**：平台层（W1~W5）+ 随包工具箱（体检/迁移/自检/报告），覆盖"长期不升级"的机器（硬约束 2）
- **拒绝**：只做平台层——现场不升级即无法受益

## 风险与规避

| 风险 | 影响 | 规避 |
|---|---|---|
| 绑定判定错误 ⇒ 向量落在错误空间 | 静默检索质量下降 | 路径(a) 强制人工确认 + 抽样检索对比（R-07a/R-09）；体检可发现"绑定模型↔空间键"不一致 |
| 重建/搬迁期间检索降级，用户以为"查不到" | 体验与信任 | 降级**显式提示**（R-04/R-03），并在重建进度页可见 |
| 表数量随模型增长 | 运维复杂度 | 模型数量有限（假设 2）；体检列出"模型↔表↔库"清单；旧表在窗口后可清理 |
| 多模型并存 ⇒ 每次检索多次嵌入调用 | 延迟上升 | 查询嵌入按模型缓存；只对命中且可达的模型扇出；各组配额限制 |
| 存量库默认重建 ⇒ 算力/时间成本 | 上线窗口压力 | 重建任务后台化 + 断点续跑 + 失败重试；升级前给出规模预估供排期 |
| 升级件在全新库/存量库表现不一致 | 新环境装不上 | 升级件写 `IF EXISTS` 幂等（L-49/L-53），两条路径都验（L-99） |
