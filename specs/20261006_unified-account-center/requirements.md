# 需求规格：unified-account-center（统一账号中心 / 消除双账号体系）

## 背景与目标

**为什么做**：本项目当前存在**两套账号体系**——后台管理端账号（admin 系）与前台普通用户账号（front 系），
分属不同登录入口、不同用户表、不同权限与组织模型。同一个人要维护两个身份，带来：
账号开通/停用/改密/找回各做两遍、权限与组织归属割裂、前后台衔接处（如前台用户使用智能体、
归属与授权）需要人工对应，长期是运维与安全成本，也是缺陷温床。

**成功长什么样（可度量）**：
1. **一套账号、一个身份源**：系统中同一自然人只有一个可登录账号身份；不存在需要人工"对应关系"的第二身份。
2. **登录入口统一**：认证收敛到单一账号中心；前后台差异只体现在**进入后的权限与界面**，不再体现为"另一套账号"。
3. **停用/改密/找回一次生效**：对某账号的禁用、改密、会话失效，对前后台全部入口同时生效。
4. **既有数据不丢**：迁移后原后台账号与原前台账号的原有关联（智能体归属、会话、文件、授权组等）全部保留且可正常访问。
5. **零回归**：既有登录、菜单权限、按钮权限、前台对话主流程与后台管理主流程全部正常。

## Non-goals（范围外）

- 不重建权限模型本身（不在本次引入 ABAC/权限点重构）——只做账号身份与认证的统一。
- 不改前台页面的信息架构与业务功能（除登录/账号入口的必要调整）。
- 不引入外部身份源（OAuth/SSO/LDAP/企业微信）——如未来要接，另立需求。
- 不做账号的强制批量合并规则（无证据的自然人重复账号**逐条人工确认**，不做自动归并）。

## 我正在做的假设

1. 「消除双账号体系」= **同一自然人只保留一个账号身份**，而不是"两套表加一个映射层继续存在两套身份"（映射层是过渡手段，不是终态）。
2. 后台账号与前台账号将收敛为**同一张用户表 + 类型/角色字段**，或**以一侧为主表、另一侧迁入**——具体路线在 plan 阶段定，本需求只约束外部可观察行为。
3. 历史数据（会话、文件、授权组、智能体归属）必须**无损迁移**，不允许"能跑就行、旧数据作废"。
4. 本次同轮纳入 **BUG-86**（P0 跨库读），与本 spec 一起在 v1.7.0 交付；BUG-86 的条款按其根因定性后单独编号。
5. 发版前不会有第三方系统依赖现有两套登录端点（若有，需在 plan 的共享面矩阵里显式列出）。
